# 交接边界 —— 谁管哪一格

本 skill 是 **Lira 的上游**。它盘点**场景、角色 · 服装、关键道具**三类资产，
给出每份几句话的需求，然后交给 Lira 去写提示词。

---

## 一、为什么这一层需要有人做

拆解 Lira 的结论（`真人口播/《Hell Grind》深度拆解/5.Lira怎么用/LIRA_SKILL_拆解笔记.md:93`）：
它在技术执行层是专家级的，但在"画面里到底该有什么内容"这个决策层是**空白**的。

而且它**不会补、也不会问**。`LIRA SKILL.md:40-41` 的 DIAGNOSE 缺口清单是：

```
Find gaps in clarity and ambiguity (camera angle, light, palette, subject count, framing)
```

**五项全是"怎么拍"，没有一项是"里面有什么"。** 所以 DETAIL 模式那 2–3 个澄清问题
不会问你陈设，BASIC 模式直接交付 —— 它会往 `[Key architectural elements]` 槽位里
填一个统计意义上最平均的场景。**那是兜底，不是补齐。**

## 二、我们管什么、Lira 管什么、图像模型管什么

| 层 | 归谁 | 例 |
|---|---|---|
| 这个剧本有几个场景/角色/道具、几个变体、每场戏用哪个 | ✅ **本 skill** | 盘点表本身 |
| 这是什么地方、什么身份、什么调性、参照物是哪件 | ✅ **本 skill** | 场景 `brief` 那几句话 |
| 这个人长什么脸、穿什么、哪件配饰是参照物 | ✅ **本 skill** | 角色底档 + 服装 `brief` |
| 这件道具是什么东西、哪处细节最好认、画上引用了谁 | ✅ **本 skill** | 道具 `brief` + `refs` |
| **地理位置与人种** —— 故事发生在哪个国家/地区、演员默认是什么人种 | ✅ **本 skill** | `meta.worldview`；个别角色例外写进该角色底档 `note` |
| **固有色** —— 这件衣服本来什么颜色、这块门牌褪成什么色 | ✅ **本 skill**（见下节修订） | "藏青夹克"、"褪成灰蓝的搪瓷门牌" |
| **配色方案** —— 色调、冷暖、比例、饱和、grade | ❌ **Lira / color-script** | 提示词里的色彩决策 |
| 机位、景别、焦段、光怎么打、tech block、摄影指导参照 | ❌ **Lira** | 它有踩过坑的公式，越界写会跟它打架 |
| **表情、情绪、姿势、动作** | ❌ **Lira / CINEDANCE** | 资产图是中性形象底板，不是一个镜头 |
| 材质纹理、叶片形状、苔痕落点、雾气、氛围 | ❌ **图像模型的先验** | 它比我们会画，别去争 |
| 这场戏结构上值不值得拍 | ❌ **higgsfield-scene-engine** | 上游 |

`build.mjs` 会拦下 `brief` 里的机位/景别/光质/调色词，
以及角色 `brief` 里的表情/姿势/性格词。

## 二之二、★ 修订：固有色归我们，配色方案归 Lira

早前这一栏写的是「配色 —— **固有色也不例外** —— 全部交给 Lira」。
加入角色与道具之后这条站不住了，**以本节为准**。理由三条：

1. **闸门本身就划在这条线上。** `DOWNSTREAM` 拦的是
   `色相 / 色调 / 饱和度 / 偏暖 / 偏冷 / 对比度 / 调色 / 影调` —— 全是配色方案的词汇，
   一个颜色名都没拦。
2. **Lira 的 `never invent a palette over them` 说的是色卡**，不是一件东西本来什么颜色。
3. **抽掉固有色，一致性就没了。** "洗旧的蓝白校服"是可验证的锚点；
   只写"洗旧的校服"，同一个角色两次生成会连衣服颜色都不一样 ——
   而那正是官方列为第二号漂移源的 character drift。
   `knowledge/scene-archetypes.md` 其实一直在建议直接写"绿色""乌黑发亮"，
   早前那一栏与它是矛盾的。

分界一句话：**"这东西本来是什么颜色"是我们的；"这张图整体往哪个方向调"是下游的。**

## 三、★ 少写才对 —— 这条是实测换来的

我曾经给每个场景写上千字规格并为每一项加闸门，**结果出图越来越差**。
而 EV 用「一个中式庭院」五个字出的图比它们都好。

三条源码印证这是设计问题不是措辞问题：

**1. Lira anti-fail #2** —— 我一直在跟它对着干：
> A tight 80–150-word prompt beats a scattered 400-word one: past a point every extra
> clause dilutes attention and **details drop out**. Cut filler; **keep anchors**.

**2. Soul Cinema 那句说了两遍** —— 模型自带的东西别去争：
> the model **carries them natively** — one register line is enough

**3. Hell Grind 的资产是 text + image** —— 图承担"长什么样"，文字承担"什么不许变"：
> An asset is a pair: text + image … **Neither works alone.**
> take only the space and the texture … **Do not use as a starting frame,
> do not inherit the composition**

**所以文字不该去干图的活。** 我们只定"有什么、几件、在哪、什么参照物"，
"长什么样"交给图像模型的先验。

## 四、一致性怎么保 —— 少写与不漂移并不矛盾

放手让先验发挥，代价是同一个院子每次生成都不一样 ——
Hell Grind 把 **environment invention** 列为头号漂移源（`evals/cases/harvest.json:45`，
`the #1 drift source`，changelog 注明 above character drift）。

解法不是穷举，是**这三样短东西**：
1. **锚点**（`brief` 里那一句）—— 不可移动、唯一、好认的参照物
2. **首图作为参考资产** —— Hell Grind 的做法：先出一张主视角图，之后所有镜头
   把它作为 location reference 传进去，并明确禁止继承构图
   （`take only the space and the texture … do not inherit the composition`）
3. **数量锁** —— 模型爱复制家具。真要锁数量时在提示词里写 `EXACT N`，
   这是下游的活，不需要我们在盘点表里逐件列出

戏份重的场景（十几场的）值得多写两句；一场过场戏一句就够。

### 三类各自的锚点是什么

同一套办法，换个载体 —— 每类资产都要有一件"不会跑掉"的东西当对齐依据：

| 类 | 锚点 | 锚点是什么性质 | 例 |
|---|---|---|---|
| 场景 | **不可移动**的物件 | **位置参照** —— 从剧本的表演位置推出来 | 正厅前那道踏道、东端那台地秤 |
| 角色 | **底档那处辨识点** + **不摘的那件配饰** | **位置参照**（配饰在身上的哪儿） | 左眉尾一道旧疤 / 腰上那条帆布工具带 |
| 道具 | **物件自身最好认的那处特征** | **不是**位置参照 —— 道具跟着人走 | 齿部三个豁口、其中一个明显崩过 |

★ **锚点的用途决定了它怎么选。** `tie the staging to it` —— 它是给下游一套
**相对位置的说法**（"跪在踏道之下""上前到第一级踏道前接旨"）。
所以场景与服装的锚点**必须落在演员真正表演的那个位置上**：
不在戏发生的地方的锚点，哪怕物件和位置都完全正确，对这场戏依然无用
（大门两侧的石狮是正确的石狮，但 1-1 的戏在正厅台基前，用不上它）。

推导顺序是**先读剧本的表演位置、再从环境里挑东西**，不是先想一件好东西再安位置 ——
反过来做就必然编造。完整的三步 + 五条判据在 `how-to-write.md` 三之三，
那一节也记了「廊柱下一对石雕瑞兽」这个踩过的坑。

★ **角色多了一层机制：底档，而且它是"首图作为参考资产"的角色版，不只是"少写一次脸"。**
脸只有一份权威版本，所有服装资产引用它 —— 这正是官方列在 environment invention 之后
的第二号漂移源（character drift）的解法，但解法不止"文字别重复写"：**不要给底档单独
出一张占位服装的过渡图（那张图没人用，纯浪费一次生成）**——拿这个角色最先建的那套
服装直接出图，这张图同时是那套服装的资产图，也是这个角色的初始状态；之后其余每一套
服装都不该独立文生图重新写一遍脸+身体+衣服 —— 那样两张图没有共同像素，一致性全靠
文字碰巧写得像，就是上一节「首图作为参考资产」想避免的做法在角色身上的翻版。
正确做法是拿第一套服装那张成图做参考生图/图生图，只改衣服，脸、发型、体型全部继承自
那张已生成的图。页面上服装格的「复制」把「底档 + 这套衣服」拼起来，那段文字对第一套
服装就是它自己的完整描述，对其余服装则是喂给参考生图的"改哪里"的指令，**不是一份
独立自足、要从零文生图的完整描述** —— 交给 Lira 时要把哪套是初始状态、其余哪几套
基于它衍生这条挑明，否则它要么给底档臆造一张占位服装图，要么各写各的脸。
（详细方法见 `how-to-write-character.md` 一之二。）

★ **道具多了一层依赖：`refs`。** 照片、油画、建筑画上引用了别的资产的形象时，
它**不能用文生图** —— 凭文字再描述一遍那张脸，出来必然不是同一个人。
必须先出被引用那份资产的成图，再以它为参考生成这件道具。
所以有 `refs` 的道具在生成顺序上排在后面，汇报时要把这条顺序说出来。

## 五、两条 Lira × color-script 冲突（备案，不影响本 skill）

**1. 颜色住在文字里还是色卡里。** Lira location 模板有固定槽位 `[Palette wrapper]`
且 anti-fail #6 要求百分比进正文；color-script 主张颜色由色卡承担、文字写色相是抢活。
**建议：色卡权威** —— Lira 自己留了门（`never invent a palette over them`，
色卡就是那个 references）。（本 skill 目前不产出任何色卡，颜色暂时整体交给 Lira 决定，
这条冲突与我们无关，纯备案。）

**2. 光质那层两边都写。** Lira tech block vs color-script 基础影调第 5 件事，
会直接矛盾（前者 `minimal fine grain`、后者"明显胶片颗粒"）。
**建议：砍掉 Lira 的 tech block**，因为 color-script 的基础影调是全片唯一一条。
