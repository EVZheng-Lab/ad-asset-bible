# ad-asset-bible（副导演-资产盘点）

Claude Code Skill：把一份剧本变成一份**资产盘点** —— 这个剧本有几处地方、
几个人几套衣服、几件跨场景的道具，每份要几个变体，每场戏用哪一个。
产出是喂给 [Lira](https://github.com/higgsfield-ai)
（Higgsfield 官方图像提示词 skill）的上游输入。

## 解决什么问题

Lira 是个**技术执行者**：它精通选模型、避坑、把一句话翻译成精确的图像提示词。
但它的 DIAGNOSE 缺口清单是 `camera angle, light, palette, subject count, framing` ——
**五项全是"怎么拍"，没有一项是"这是哪儿、这是谁、有几个"**。它不会补，也不会问。

这个缺口在整个 Higgsfield 官方开源体系里都是真空，而且官方自己知道：

- `evals/cases/harvest.json` 把 **environment invention** 列为
  `the #1 drift source`（changelog 里特意注明 *above character drift*），
  解法是一条 regex 强制的锁 —— `The set contains only what the reference shows.`
  **锁造好了，填锁的东西没造。**
- 那句 *above character drift* 顺便说明了**第二号漂移源是角色**，同样没有 inventory。
- `docs/Seedance 2 Skill.md` 给了做美术设计的授权，没给方法。
- 官方 changelog 亲手记录：八条 *World Through Recurrence* 轴指向的那个
  `"named worlds" / "world-typing" inventory` **不存在**。

ad-asset-bible 就是那个 inventory。

## 产出什么

一个自包含 HTML 页，**三个 Tab、每个 Tab 一张结构相同的表**，每张四列：**序号 | 资产 | 需求描述 | 变体**。
页面顶部剧本路径正下方还有一条高亮的**世界观小结**（年代/阶层/风格的结论，见下文）。

| Tab | 第一列长什么样 | 变体那一列 |
|---|---|---|
| **场景** | `@loc_shenfu` 沈家 · 正院<br>场次 5-1 6-1 8-2 …（15 场） | 炭火带 · 反打 |
| **角色 · 服装** | `@char_along` 阿龙（底档：脸/身形，写一遍）<br>└ `@char_along_gongzhuang` 阿龙 · 工装 | 破损沾油 |
| **关键道具** | `@prop_yupei` 定情玉佩<br>场次 5-1 30-2 | 碎裂 |

Tab 栏右端有一个**「全部展开」**开关（也可以直接用 `?tab=all`）——
三张表同时铺开，跨表 Ctrl+F 和一次截全都靠它。
`?row=N` 深链会**自动切到那一行所在的那张表**再高亮滚过去。
角色/道具为空时对应 Tab 不出现，只剩一张表时整个 Tab 栏都不出（纯场景盘点仍然合法）。

每行三个「复制」各给一样东西，**都不带标签、场次这类账目信息**（粘进提示词里是纯噪声）：
**第一列给资产名**（`沈云卿 · 诰命礼服`，拿去当文件名或指代）、
**第二列给需求描述原文**（服装格前面拼上底档，有蓝框的道具附一句参考生图说明）、
**变体格只给本变体那一句改动**（不重复基础描述）。

它**不生成图像**，不调用 Lira，不改剧本，**也不写配色方案** ——
色调冷暖比例交给 Lira 与 color-script；但**固有色是我们的**
（"藏青夹克"是识别特征，不是调色决策）。

## ★ 核心结论：描述刻意只有几句话

这个 skill 走偏过一次。为了让出图"更真实"，曾给每个场景写上千字规格 ——
尺度到厘米、材分制、11 件带位置的道具表 —— 并为每一项加了闸门。**结果图越来越差。**
而用「一个中式庭院」五个字出的图比它们都好。

原因：图像模型对"中式庭院"这类空间有极强先验（成千上万张园林照片，隐含几百样细节），
穷举清单等于说"就这些，别的没有"，把先验压掉了。而尺寸材分这类字图像模型根本渲不出来，
纯占注意力预算 —— Lira anti-fail #2 早就写着
`past a point every extra clause dilutes attention and details drop out`。

所以定位是**资产盘点**，每份需求描述卡在 300 字：只写这是什么东西、什么档次、什么调性、
哪一处是认得出的参照物。**不写尺寸、不写材料清单、不写机位光线。**

★ **这条对角色和道具一样成立**：模型对"二十七八岁男性方脸"和"一把老式黄铜钥匙"
的先验同样强，穷举五官比例只会更差。

## 四条设计要点

**1. 只写"这是什么"，不写"怎么拍、怎么调"。**
机位/景别/光质/调色是 Lira 与 color-script 的活；**表情、姿势、性格**也不写 ——
资产图是中性的形象底板，不是一个镜头。`build.mjs` 有 31 个下游词
加两张角色专用词表（表情姿态 / 性格评语）的禁词校验。

**2. 去重靠台词证据，不靠地名。**
剧本里同一处会有好几个叫法，不同处也会共用一个名字。实跑《归来凤栖处》时四种都遇到了：
一名多地、多名一地、地名指错、一院多空间。去重依据写进 `note`，这是使用者最要复核的一项。

**3. 三类共用同一条变体判据：主资产那个东西，在这个变体里还在画面里吗？**
在 = 变体（图生图有共同像素）；不在 = 另一份资产。
所以换机位、下雨、烧成废墟、衣服撕破、玉佩碎裂都是变体；
**镜头搬进另一个房间、换一整套衣服、换成一枚仿制的玉佩都不是** ——
混进来的代价是双份的：图生图必然失败，而且**盘点上漏掉一份真实要拍的资产**。

**4. 三类同住一份 JSON，模型只写 JSON、不写 HTML。**
同住一份不是图省事：道具的 `refs`（这件道具画面上引用了谁的形象）要能被校验
"你引用的那个 tag 确实存在"，拆成三份数据源就拦不住拼错一个字。
交叉对账也一样 —— **角色/道具的场次必须都在场景表里出现过**，
有人有道具却没有地方 = 场景表漏了一场。
样式全部由 `templates/report-shell.html` 承担，`build.mjs` 负责套模板 + 结构预检；
JSON 里出现任何 HTML/CSS 会被直接拒绝生成。页面里有一条 SELFTEST 横条作为产出合格的凭证，
但它**默认不显示给人看**（自检靠 `--dump-dom` 抓，肉眼看要加 `?selftest=1`）。

## 三个概念上最容易搞错的地方

| | 正确做法 | 为什么 |
|---|---|---|
| **角色的三层** | 底档（脸，写一遍）+ 每套服装一份资产 + 状态变体 | 出图单元是「角色 + 一套服装」—— 光有一张脸出不了图；而每份服装各写一遍脸就是 character drift |
| **道具的收录门槛** | 只收**跨场景**的 | 只有跨场景复用的东西才有漂移风险、才值得建资产锁；用一次的道具列出来反而是在压先验 |
| **间接引用** | 照片/油画/建筑画上画着谁 → `refs` 登记，**必须走参考生图** | 凭文字再描述一遍那张脸，出来必然不是同一个人。refs 要指到**服装级/场景级**，指到角色底档没用（照片上这人穿的是哪套？） |

## 目录结构

```
ad-asset-bible/
├── SKILL.md                        # skill 主体：工作流程 + 边界 + 禁止清单
├── references/
│   ├── how-to-write.md             # 场景篇 + 三类共用纪律（切场景/去重/brief/变体/考据分寸）
│   ├── how-to-write-character.md   # 角色篇：三层压两层 / 收录门槛 / 换装不是变体 / 不写表情性格
│   ├── how-to-write-prop.md        # 道具篇：跨场景门槛 / 状态变体 / refs 与参考生图
│   └── handoff-boundaries.md       # 谁管哪一格 + 三类各自的锚点 + 一致性怎么保
├── knowledge/
│   ├── scene-archetypes.md         # 场景调性速查：身份定形制、旧≠没人管、时代错误清单
│   └── costume-archetypes.md       # 服装调性速查：身份定服制、别抄服制术语、衣服的旧
├── scripts/
│   ├── build.mjs                   # JSON → HTML，含按资产类型分派的结构预检
│   ├── check-sync.mjs              # 外壳与 build.mjs 的常量同步检查
│   └── make-test.mjs               # 闸门验收工具（非运行时）
├── templates/
│   └── report-shell.html           # 静态外壳，一个字都不动
└── tests/fixtures/ok.json          # 合规样本（含三类资产），make-test 从它派生 36 个违规样本
```

## 安装

```bash
# 项目级
git clone <repo> .claude/skills/ad-asset-bible
# 或全局
git clone <repo> ~/.claude/skills/ad-asset-bible
```

需要 Node.js（脚本是 ESM `.mjs`，无第三方依赖）。脚本用 `import.meta.url` 自定位，
从任何 cwd 调用都一样，整个目录拷走就能用。

装完跑一次闸门验收：

```bash
cd ad-asset-bible && node scripts/check-sync.mjs && node scripts/make-test.mjs
```

## 用法

### 单独用 —— 只要一份资产盘点

```
/ad-asset-bible [剧本路径]
```

路径可省，不传时从当前对话判断。也可以直接说「这个剧本有哪些场景」「出个资产盘点」
「有哪些角色、几套服装」「关键道具有哪些」「几个场景几个变体」「给 Lira 的场景描述」。

角色与道具两张表是**可选的** —— 只做场景盘点仍然合法，空的那张表整节隐藏。

### ★ 推荐：让 Agent 串起本 skill → Lira，一步拿到带提示词的表

不用把每一份需求描述一条条复制去喂 Lira——让 Agent 自己调度两个 skill：

1. **建一个项目文件夹，把剧本复制进去。**
2. **打开任意 Agent 工具**（Claude Code / Cursor 等），把本 skill 和
   [Lira](https://github.com/higgsfield-ai) 都装上（安装方式见上一节）。
3. **在 Agent 工具里进入这个项目文件夹**，启用本 skill，然后一句话说清两段活：

   > 把这个路径下的剧本拆解成资产盘点，然后把结果交给 Lira skill，
   > 让 Lira 在产出的网页表格里加一列「Lira Prompt」，把它为每一份资产写的提示词填进这一列。

最后拿到的是一张**需求描述与图像提示词并排**的表，照着一行行出图就行，
中间不用人工搬运。

> ⚠️ **「Lira Prompt」列是下游追加的，`build.mjs` 本身只产出四列**
> （序号 | 资产 | 需求描述 | 变体，表头写死在 `templates/report-shell.html` 里）。
> 所以**重跑一次 `build.mjs` 会重新生成整个页面、把这一列冲掉** ——
> 补完提示词就别再重跑；要留存就把带提示词的那份另存一个文件名。
> 反过来说，**盘点内容需要改的时候，是改 JSON 重跑 build.mjs、再重新补提示词**，
> 不要直接手改 HTML（那会让页面与数据脱节，SELFTEST 横条也就失去意义）。

## 与姊妹 skill 的分工

| skill | 管什么 | 关系 |
|---|---|---|
| `higgsfield-scene-engine` | 这场戏结构上值不值得拍 | 上游 |
| `higgsfield-character-design` | 人物与世界观（人设本身） | 平级 |
| **ad-asset-bible** | 有几个场景/角色/道具、每份是什么东西 | —— |
| `color-script` | 全片影调统一（基础影调 + 每场戏的 grade 色卡） | 平级 |
| `Lira` | 资产需求 → 图像提示词，选模型、避坑 | 下游 |
| `CINEDANCE` / `h3-seedance-prompt` | 视频提示词、镜头、表演 | 下游的下游 |
