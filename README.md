# ad-asset-bible（副导演-资产盘点）

Claude Code Skill：把一份剧本变成一份**资产盘点** —— 这个剧本有几处地方、
几个人几套衣服、几件跨场景的道具，每份要几个变体，每场戏用哪一个。
产出是喂给 [Lira](https://github.com/higgsfield-ai)
（Higgsfield 官方图像提示词 skill）的上游输入。

## 解决什么问题

Lira 是个**技术执行者**：它精通选模型、避坑、把一句话翻译成精确的图像提示词。
但它的 DIAGNOSE 缺口清单是 `camera angle, light, palette, subject count, framing` ——
**五项全是"怎么拍"，没有一项是"这是哪儿、这是谁、有几个"**。它不会补，也不会问。

这个缺口在整个 Higgsfield 官方开源体系里都是真空，而且官方自己知道：

- `evals/cases/harvest.json` 把 **environment invention** 列为
  `the #1 drift source`（changelog 里特意注明 *above character drift*），
  解法是一条 regex 强制的锁 —— `The set contains only what the reference shows.`
  **锁造好了，填锁的东西没造。**
- 那句 *above character drift* 顺便说明了**第二号漂移源是角色**，同样没有 inventory。
- `docs/Seedance 2 Skill.md` 给了做美术设计的授权，没给方法。
- 官方 changelog 亲手记录：八条 *World Through Recurrence* 轴指向的那个
  `"named worlds" / "world-typing" inventory` **不存在**。

ad-asset-bible 就是那个 inventory。

★ **同一个缺口在表演上也存在，所以还多产出一层「角色档案」。**
`ACTING SKILL.md` 把表演写得极专业（五支柱、坏表演图谱 15 条、0–5 分表演量表），
但它跟 Lira 犯的是同一个毛病：**假设"这个人是谁"已经现成存在**，
谁都不负责从剧本里把性格、脾气、习惯动作、声线提炼出来。
而缺了这份底本，下游每个镜头把同一个情绪各自翻成一串动作 ——
这次看手表、下次搓裤缝、再下次咬指甲，三次之间没有任何东西保证是同一个人的习惯。
**那就是 character drift 在行为层的翻版，跟"每份服装各写一遍脸"是同一个病。**

★★ **而这个洞还有第二半，是后来才补上的。** ACTING §8.2 那句
`Never contradict the master` 把"每场改写、核不动"这把锁造得极好，
**却没人负责告诉它"现在改写的是哪个时期的他"** —— 它假设一份档案全片有效。
于是有弧光的角色（开篇活泼开朗、后半段变得沉默）交给它只有一张卡：
它没有依据知道该往沉默演，那把锁还会主动把它按回开朗，一路照开朗演到底。
所以角色档案里那八块是**开场状态**，另有一栏 `arc[]`「后来变了什么」——
详见下文「第四块」。

## 产出什么

一个自包含 HTML 页，**五个 Tab**。前四个各是一张结构相同的表，每张四列：**序号 | 资产 | 需求描述 | 变体**；
第五个是**「角色档案」**（卡片，不是表）。
页面顶部剧本路径正下方还有一条高亮的**世界观小结**（年代/阶层/风格/地理位置/人种的结论，见下文）。

| Tab | 第一列长什么样 | 变体那一列 |
|---|---|---|
| **场景** | `@loc_shenfu` 沈家 · 正院<br>场次 5-1 6-1 8-2 …（15 场） | 炭火带 · 反打 |
| **角色 · 服装** | `@char_along` 阿龙（底档：脸/身形，写一遍）<br>└ `@char_along_gongzhuang` 阿龙 · 工装 | 破损沾油 |
| **关键道具** | `@prop_yupei` 定情玉佩<br>场次 5-1 30-2 | 碎裂 |
| **特效** | `@vfx_chongjibo` 阿龙的冲击波<br>发出者 `@char_along` | 蓄力 |
| **角色档案** | `@char_along` 阿龙 —— 一人一张卡<br>八块 = 开场状态，下面挂「后来变了什么」 | 没有变体（见下）；但有**阶段** |

Tab 栏右端有一个**「全部展开」**开关（也可以直接用 `?tab=all`）——
所有块同时铺开，跨表 Ctrl+F 和一次截全都靠它。
`?row=N` 深链会**自动切到那一行所在的那张表**再高亮滚过去（档案是卡片，指不到）。
角色/道具为空时对应 Tab 不出现，只剩一张表时整个 Tab 栏都不出（纯场景盘点仍然合法）。

每行三个「复制」各给一样东西，**都不带标签、场次这类账目信息**（粘进提示词里是纯噪声）：
**第一列给资产名**（`沈云卿 · 诰命礼服`，拿去当文件名或指代）、
**第二列给需求描述原文**（服装格前面拼上底档，有蓝框的道具附一句参考生图说明）、
**变体格只给本变体那一句改动**（不重复基础描述）。

### 第四块：角色档案

**建了底档的角色一律有一份**（多一份、少一份 `build.mjs` 都拦）。它写的是
**这个人怎么演、说话什么声**：体态与来历 / 心理引擎 / 说话在戏里怎么变 /
习惯动作（每条带触发条件）/ 步态（要取名）/ 面具裂开的条件 /
唯一让他软下来的那个 / 眼睛怎么活，外加 **Voice 四要素**（音区·速度·口音·腔调）
和 **贯穿全片的目标**。字段与块序照 `ACTING SKILL.md` §6 抄，
官方原文 `block order is fixed`。

★ **它不是第四张同构表，因为它不是出图资产** —— 不出图、也不进图像提示词。
它没有变体（变体是"同一张图变化之后"，档案压根不出图），
也不登记场次（那八块每场都用得上）。

### ★★ 那八块写的是「开场状态」，不是「全片恒定」

这一条是改过来的，值得单说 —— 早前这里写着"档案是全片恒定的底本"，
**那句话对有弧光的角色是假的**：

一个人开篇活泼开朗、后半段变得沉默，这个转变要靠表演演出来。而档案里只写了"活泼开朗"，
下游（ACTING）手上只有这一张卡 —— 它没有任何依据知道该往沉默演，
官方 §8.2 那句 `Never contradict the master` 还会主动把它按回开朗。
**它只会一路照开朗演到底。**

**这跟官方那两个洞是同一种洞**：Lira 把"怎么拍"做到专家级却不管"画面里有什么"；
ACTING 把"每场改写"这把锁造得极好，**却没人负责告诉它"现在改写的是哪个时期的他"**。

所以多出一栏 **`arc[]`「后来变了什么」**，一段一个阶段：
**触发的那件事**（锚事件，不锚场次 —— 剪辑调序也不失效）+ **他因此成了什么样**
（只写变了的，没变的不重写）+ 声音真变了可以另给一整套四要素。
页面按阶段各给一个「复制档案·〈那件事〉」，点它拿到的是
**开场 + 累积到这一段的所有变化**，已经拼好，不用自己合并。

★ **arc 只记事实，不记时机** —— 这是最要紧的一条分工：
「儿子被带走那天之后她变了」是**事实**（谁去查剧本都是这个答案，不需要眼光，只需要仔细）；
「从第 48 场起让观众察觉」是**节奏判断**（同一件事，导演可以让观众提前预感到，
也可以突然给一记重锤，两个导演的答案不一样）。
**后者归导演，本 skill 不给** —— 写进去了导演就没得选了。`build.mjs` 有闸门专门拦它。

★ **没有弧光的角色 `arc` 留空，开场状态就等于全片状态 —— 合法，不算漏项。**
功能性角色（喜剧配角、只推剧情的）本来就不该有弧光，别给每个角色都硬铺三段。

★ **也别退而求其次去锁"少数几个字段"**：曾想过"声音、步态、习惯动作锁死不变，
只让心理引擎跟着变"，站不住 —— 那是把**硬件**和**软件**搞混了。缺胳膊、疤痕是硬件
（在底档里，本来就不变）；声音、习惯动作、走路样子**全都是"这个人现在心里什么状态"
的外在表现**，是软件，压垮了就都会变，甚至会长出一个原来没有的新习惯动作。
真正永不变的只有身体事实（底档）和**他身上发生过的那件事**（过去时）。

★ **两类复制按钮给的是两种生命周期不同的东西**：
「复制档案」给表演底本（**表演每场改写**）；
「复制声音」给 Voice prompt —— **原样贴进 audio 字段、每次说话都贴、不按场次改**。
项目书那句 `The voice is not an asset` 说的是它不需要图，不是说它不用锁。
（"不按场次改"不等于"永远不会变"—— 声音真的随弧光变了，在那个阶段另给一版，
但**换哪一版是导演的判断**，官方那套只有一个声音格子、自己做不了这个选择。）

★ **底档不单独出图，第一套服装的成图就是初始状态。** 不要给底档单独生成一张占位服装
的过渡图（那张图没人用，纯浪费一次生成）——这个角色最先建的那套服装直接出图，
这张图同时是那套服装的资产图，也是这个角色的初始状态；其余每一套服装都该拿它的成图
做参考生图/图生图衍生、只改衣服，不是各自独立文生图重写一遍脸。服装格拼出来的
「底档 + 这套衣服」，对第一套是它自己要出的完整描述，对其余服装是喂给参考生图的
"改哪里"指令 —— 不是拿这段拼接文字去跑一次从零开始的文生图，那样两张图没有共同像素，
character drift 又回来了。交给 Lira 时把哪套是初始状态这条挑明。

它**不生成图像**，不调用 Lira，不改剧本，**也不写配色方案** ——
色调冷暖比例交给 Lira 与 color-script；但**固有色是我们的**
（"藏青夹克"是识别特征，不是调色决策）。

## ★ 核心结论：描述刻意只有几句话

这个 skill 走偏过一次。为了让出图"更真实"，曾给每个场景写上千字规格 ——
尺度到厘米、材分制、11 件带位置的道具表 —— 并为每一项加了闸门。**结果图越来越差。**
而用「一个中式庭院」五个字出的图比它们都好。

原因：图像模型对"中式庭院"这类空间有极强先验（成千上万张园林照片，隐含几百样细节），
穷举清单等于说"就这些，别的没有"，把先验压掉了。而尺寸材分这类字图像模型根本渲不出来，
纯占注意力预算 —— Lira anti-fail #2 早就写着
`past a point every extra clause dilutes attention and details drop out`。

所以定位是**资产盘点**，每份需求描述卡在 300 字：只写这是什么东西、什么档次、什么调性、
哪一处是认得出的参照物。**不写尺寸、不写材料清单、不写机位光线。**

★ **这条对角色和道具一样成立**：模型对"二十七八岁男性方脸"和"一把老式黄铜钥匙"
的先验同样强，穷举五官比例只会更差。

## 四条设计要点

**1. 只写"这是什么"，不写"怎么拍、怎么调"。**
机位/景别/光质/调色是 Lira 与 color-script 的活；资产的需求描述里**表情、姿势、性格**
也不写 —— 资产图是中性的形象底板，不是一个镜头。`build.mjs` 有 31 个下游词
加两张角色专用词表（表情姿态 / 性格评语）的禁词校验。
★ **性格有正当去处（角色档案），但那不给需求描述任何豁免** ——
**双向墙**：档案禁服装与相貌（`No wardrobe. The profile must survive any costume change.`），
需求描述禁性格与表情，两边都有闸门。少掉任何一边，两层就互相污染，
而污染的症状（角色前后不像同一个人）跟锚点错误一样**无法由单张图发现**。

**2. 去重靠台词证据，不靠地名。**
剧本里同一处会有好几个叫法，不同处也会共用一个名字。实跑《归来凤栖处》时四种都遇到了：
一名多地、多名一地、地名指错、一院多空间。去重依据写进 `note`，这是使用者最要复核的一项。

**3. 三类共用同一条变体判据：主资产那个东西，在这个变体里还在画面里吗？**
在 = 变体（图生图有共同像素）；不在 = 另一份资产。
所以换机位、下雨、烧成废墟、衣服撕破、玉佩碎裂都是变体；
**镜头搬进另一个房间、换一整套衣服、换成一枚仿制的玉佩都不是** ——
混进来的代价是双份的：图生图必然失败，而且**盘点上漏掉一份真实要拍的资产**。
（角色档案不适用这条 —— 它根本没有变体。）

**4. 四类同住一份 JSON，模型只写 JSON、不写 HTML。**
同住一份不是图省事：道具的 `refs`（这件道具画面上引用了谁的形象）要能被校验
"你引用的那个 tag 确实存在"，拆成三份数据源就拦不住拼错一个字。
交叉对账也一样 —— **角色/道具的场次必须都在场景表里出现过**，
有人有道具却没有地方 = 场景表漏了一场。
**角色档案住这一份的理由同构但换了一条**：它要被校验"每个底档有且只有一份档案" ——
拆成独立 skill 就会有两套 `@char_` 命名空间、两份各自盘出来的角色名单，
谁也拦不住"档案里多一个人、少一个人"。
样式全部由 `templates/report-shell.html` 承担，`build.mjs` 负责套模板 + 结构预检；
JSON 里出现任何 HTML/CSS 会被直接拒绝生成。页面里有一条 SELFTEST 横条作为产出合格的凭证，
但它**默认不显示给人看**（自检靠 `--dump-dom` 抓，肉眼看要加 `?selftest=1`）。

## 三个概念上最容易搞错的地方

| | 正确做法 | 为什么 |
|---|---|---|
| **角色的三层** | 第一套服装出图当初始状态（底档脸只写一遍，不单独出占位服装图）+ 其余服装基于它做参考生图衍生 + 状态变体 | 出图单元是「角色 + 一套服装」；服装若各自独立文生图重写脸，就是 character drift —— 要靠参考生图继承脸/身体，不是文字碰巧写得像；给底档单独出占位服装图则是白烧一次生成 |
| **道具的收录门槛** | 只收**跨场景**的 | 只有跨场景复用的东西才有漂移风险、才值得建资产锁；用一次的道具列出来反而是在压先验 |
| **间接引用** | 照片/油画/建筑画上画着谁 → `refs` 登记，**必须走参考生图** | 凭文字再描述一遍那张脸，出来必然不是同一个人。refs 要指到**服装级/场景级**，指到角色底档没用（照片上这人穿的是哪套？） |
| **角色档案的五种生命周期** | ① 外观 descriptor 逐字复制进每条提示词 ② Voice prompt 原样贴 audio、**不按场次改** ③ 表演档案（八块 = **开场状态**）每场**改写、核不动** ④ 每镜的表情动作是下游现写 ⑤ **阶段状态**（`arc[]`）= 发生了什么事、他因此成了什么样 | 五者混成一件事是最常见的错：把声音每场重写一遍、把表演档案当成某个镜头的描述、或者把八块当成全片唯一那一版（有弧光的角色就会一路照开场演到底）。★ 还有两条容易漏：物理上做不到的行为要**转移不要删**（爱踱步的人坐下了，同样的劲头变成晃腿、敲手指）；**"这场戏用哪个阶段"是导演的判断，不是让下游自己挑** |

## 安装

```bash
# 项目级
git clone <repo> .claude/skills/ad-asset-bible
# 或全局
git clone <repo> ~/.claude/skills/ad-asset-bible
```

需要 Node.js（脚本是 ESM `.mjs`，无第三方依赖）。脚本用 `import.meta.url` 自定位，
从任何 cwd 调用都一样，整个目录拷走就能用。

装完跑一次闸门验收：

```bash
cd ad-asset-bible && node scripts/check-sync.mjs && node scripts/make-test.mjs
```

## 用法

### 单独用 —— 只要一份资产盘点

```
/ad-asset-bible [剧本路径]
```

路径可省，不传时从当前对话判断。也可以直接说「这个剧本有哪些场景」「出个资产盘点」
「有哪些角色、几套服装」「关键道具有哪些」「几个场景几个变体」「给 Lira 的场景描述」
「角色档案」「这个角色怎么演」「角色性格声线」「给 ACTING 的表演档案」。

角色与道具两张表是**可选的** —— 只做场景盘点仍然合法，空的那张表整节隐藏。
但**角色档案不是可选的**：建了底档的角色一律要有一份（多一份少一份都会被拒）。

### ★ 推荐：让 Agent 串起本 skill → Lira，一步拿到带提示词的表

不用把每一份需求描述一条条复制去喂 Lira——让 Agent 自己调度两个 skill：

1. **建一个项目文件夹，把剧本复制进去。**
2. **打开任意 Agent 工具**（Claude Code / Cursor 等），把本 skill 和
   [Lira](https://github.com/higgsfield-ai) 都装上（安装方式见上一节）。
3. **在 Agent 工具里进入这个项目文件夹**，启用本 skill，然后一句话说清两段活：

   > 把这个路径下的剧本拆解成资产盘点，然后把结果交给 Lira skill，
   > 并告诉它这个片子的长宽比是 9:16（竖屏短剧；横屏片写 16:9）。
   > 角色不单独给底档出占位服装图——每个角色最先建的那套服装直接出图，当这个角色的
   > 初始状态；同一角色其余每套服装都要基于这张成图做参考生图/图生图衍生（只改衣服，
   > 不要重新独立文生图整套脸和身体）。
   > 让 Lira 在产出的网页表格里加一列「Lira Prompt」，把它为每一份资产写的提示词填进这一列。

★ **长宽比这一句别省，而且只能你来给。** 本 skill 只回答「有几份资产、每份是什么东西」，
按分工**不决定怎么拍**（机位、景别、画幅都不归它管，见下面「与姊妹 skill 的分工」）；
而 Lira 要写出可直接出图的提示词，画幅是必需参数。两头都不猜，所以它得由你在这一句里交代。

最后拿到的是一张**需求描述与图像提示词并排**的表，照着一行行出图就行，
中间不用人工搬运。

> ⚠️ **「Lira Prompt」列不是 `build.mjs` 的产物。** 它只出四列（序号 | 资产 | 需求描述 | 变体，
> 表头写死在 `templates/report-shell.html` 里），这一列是 Lira 在页面生成之后补上去的。
> 所以**要返工就让 Agent 重跑整条链（盘点 → Lira），而不是只重跑 `build.mjs`** ——
> 单跑前半段只会得到一张没有提示词列的新页面。
> 同理，盘点内容要改是**改 JSON、重跑整条链**，不要直接手改 HTML
> （手改会让页面与数据脱节，SELFTEST 横条也就失去意义）。

## 与姊妹 skill 的分工

| skill | 管什么 | 关系 |
|---|---|---|
| `higgsfield-scene-engine` | 这场戏结构上值不值得拍 | 上游 |
| `higgsfield-character-design` | 人物与世界观（人设本身） | 平级 |
| **ad-asset-bible** | 有几个场景/角色/道具、每份是什么东西；**外加每个角色怎么演、说话什么声、后来变成了什么样** | —— |
| `color-script` | 全片影调统一（基础影调 + 每场戏的 grade 色卡） | 平级 |
| `Lira` | 资产需求 → 图像提示词，选模型、避坑 | 下游 |
| **导演（人）** | **这场戏用哪个阶段** —— 从第几场起让观众看见他变了 | 中间那一道，**不归任何 skill** |
| `ACTING` | 拿（导演选定那个阶段的）角色档案 → 每场改写成当场的表演段落 | 下游 |
| `CINEDANCE` / `h3-seedance-prompt` | 视频提示词、镜头、每镜的表情与动作 | 下游的下游 |

★ **跟 ACTING 的分界**：ACTING 精通"怎么写活的表演"（五支柱、坏表演图谱、表演量表），
但它**假设"这个人是谁"已经现成存在**。我们负责从剧本里把那个人提炼出来并锁住；
它负责每场把这份档案改写进当场的姿态与动作。

**分三段，别说成两段：**

| | 归谁 | 性质 |
|---|---|---|
| 开场是什么样 + 发生了什么事、他因此成了什么样 | **我们** | **事实** —— 谁去查剧本都是这个答案 |
| 从第几场起，让观众看见他变了 | **导演** | **节奏判断** —— 两个导演答案不一样 |
| 这一个镜头此刻的表情与姿势 | **ACTING / CINEDANCE** | 每镜现写 |

★ 早前这里写的是「**恒定的归我们，此刻的归它**」—— **那个二分是错的**，
它漏掉了中间那一层。一个人后半段变了，"变了"这件事既不恒定、也不是某一镜此刻，
二分表里没有它的位置，于是被当成噪声过滤掉，下游拿着开场那一版一路演到底。
